## 🧭 1. ภาพลวงตาของความเร็ว (The Illusion of Speed)

ในวงการวิศวกรรมซอฟต์แวร์ยุคใหม่ เรามักเห็นโครงการโอเพนซอร์สเปิดตัวพร้อมกราฟแท่งเปรียบเทียบความเร็วอันน่าตื่นตาตื่นใจ:
> *"เร็วขึ้น 10 เท่า! ประหยัดแรม 5 เท่า!"*

แต่เมื่อนำเครื่องมือเหล่านั้นไปติดตั้งในระบบงานจริง (Production) สิ่งที่มักตามมาคือฝันร้าย:
* สคริปต์บิลด์ของ Xcode หรือ Make พังกลางคัน เพราะ Shell คืน Exit Code ไม่ตรงกับมาตรฐาน
* ไฟล์การตั้งค่าเสียหาย เพราะตัวขยายสตริงตัดช่องว่างทิ้งโดยพลการ
* ตัวแปรสภาพแวดล้อมหายไปบางตัว ทำให้โปรแกรมหาไลบรารีไม่เจอ

นี่คือสัจธรรมที่ผู้ประพันธ์ยึดถือเป็นเสาหลักสูงสุดในการสร้าง `zbash`:
> **"เร็วแต่ผลลัพธ์ผิด คือไร้ค่า — เร็วและถูกต้องตรงกันบิตต่อบิต คือการปฏิวัติ"**

ความเร็วในการประมวลผลจะไม่มีความหมายใดๆ เลย หากข้อมูลผิดพลาดแม้แต่ไบต์เดียว หรือพฤติกรรมผิดเพี้ยนไปจากมาตรฐานที่โลกใช้งานมา 40 ปี

ในบทนี้ เราจะมาเจาะลึกปรัชญาของ **Differential Parity Testing (การทดสอบเทียบเคียงเชิงอนุพันธ์)** ซึ่งเป็นระเบียบวิธีวิจัยและการทดสอบทางวิศวกรรมที่ทำให้ `zbash` สามารถยืนหยัดแทนที่ GNU Bash ได้อย่างแท้จริง!

## 🏗️ 2. ทำไม Unit Test ธรรมดาจึงไม่เพียงพอสำหรับ Shell?

ในการพัฒนาแอปพลิเคชันทั่วไป เรามักเขียน Unit Test เช่น:
```c
assert(add(2, 3) == 5);
assert(strlen("hello") == 5);
```
แต่วิธีการนี้ล้มเหลวอย่างสิ้นเชิงเมื่อนำมาใช้ทดสอบ **Unix Shell**:
1. **พื้นที่สถานะกว้างใหญ่ระดับอนันต์ (Combinatorial State Space):** สคริปต์เชลล์สามารถผสมผสาน Quoting, Wildcards, ท่อไปป์, Redirections, Subshell, และตัวแปร เข้าด้วยกันได้นับล้านรูปแบบ ไม่มีใครสามารถเขียน Assertion ครอบคลุมได้ทั้งหมดด้วยมือ
2. **มาตรฐานที่ไม่เคยถูกบันทึก (Undocumented Quirks):** พฤติกรรมของ Bash หลายอย่างไม่ได้เขียนอยู่ในมาตรฐาน POSIX แต่เกิดขึ้นจากประวัติศาสตร์การแก้ไขบั๊กตลอด 35 ปี ซึ่งสคริปต์ระบบนับล้านตัวพึ่งพาพฤติกรรมเหล่านั้นโดยไม่รู้ตัว

ทางออกทางวิศวกรรมเพียงหนึ่งเดียวคือ: **อย่าเดาผลลัพธ์เอง แต่จงใช้ "ผู้พิทักษ์แห่งประวัติศาสตร์" มาเป็นมาตรวัดความจริง!**

## 🔍 3. สถาปัตยกรรม Differential Testing

แนวคิดของ Differential Testing คือการนำระบบใหม่ที่เราสร้าง (`zbash`) มาประชันกับระบบมาตรฐานดั้งเดิมของระบบปฏิบัติการ (**macOS `/bin/bash`**) โดยรันคำสั่งเดียวกัน ในสภาพแวดล้อมเดียวกัน แล้วจับผลลัพธ์มาเปรียบเทียบกันแบบตาต่อตา ฟันต่อฟัน:

```
                            [ Script Test Case ]
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
        [ Golden Baseline ]                     [ Under Test (SUT) ]
         macOS /bin/bash                              zbash
                 │                                       │
         ┌───────┴───────┐                       ┌───────┴───────┐
         ▼               ▼                       ▼               ▼
     [ stdout ]      [ exit code ]           [ stdout ]      [ exit code ]
         │               │                       │               │
         └───────────────┼───────────────────────┘               │
                         ▼                                       ▼
                 [ diff / cmp -s ]                       [ rc1 == rc2 ]
                         │                                       │
                         └───────────────────┬───────────────────┘
                                             ▼
                                  [ PASS / FAIL VERDICT ]
```

### เกณฑ์การตัดสินความถูกต้อง (Verification Criteria):
การทดสอบแต่ละข้อจะผ่าน (PASS) ได้ ก็ต่อเมื่อ:
1. **เอาต์พุตมาตรฐาน (STDOUT):** ต้องตรงกันแบบบิตต่อบิต 100% (`cmp -s` หรือการตัดอักขระส่วนเกินที่เหมือนกัน)
2. **รหัสสถานะการสิ้นสุด (Exit Code `$?`):** ต้องตรงกันทุกตัวเลข (เช่น 0 กับ 0, 127 กับ 127, 2 กับ 2)

หากมีความแตกต่างเพียงเศษเสี้ยวของช่องว่าง หรือตัวเลข Exit code ผิดเพี้ยนไปแม้แต่ 1 ค่า การทดสอบข้อนั้นจะถูกตัดสินว่า **FAIL ทันที**

## ⚙️ 4. เจาะลึกโค้ด Harness ใน `common.sh`

ดูโค้ดจริงใน [`test/1000-test/common.sh`](test/1000-test/common.sh) ที่ขับเคลื่อนการทดสอบนับพันข้อ:

```bash
# ไฟล์: test/1000-test/common.sh
run_test() {
    local test_num="$1"
    local desc="$2"
    local cmd="$3"

    # 1. รันบน macOS /bin/bash (Golden Baseline)
    BASH_OUT=$(/bin/bash -c "$cmd" 2>&1)
    BASH_RC=$?

    # 2. รันบน zbash (Bare-Metal Engine)
    ZBASH_OUT=$("$ZBASH_BIN" -c "$cmd" 2>&1)
    ZBASH_RC=$?

    # 3. เปรียบเทียบผลลัพธ์
    if [ "$BASH_RC" -eq "$ZBASH_RC" ] && [ "$BASH_OUT" = "$ZBASH_OUT" ]; then
        PASS_COUNT=$((PASS_COUNT + 1))
        echo -e "  [PASS] Test #$test_num: $desc"
    else
        FAIL_COUNT=$((FAIL_COUNT + 1))
        echo -e "  [FAIL] Test #$test_num: $desc"
        echo -e "    COMMAND: $cmd"
        echo -e "    EXPECTED RC: $BASH_RC, GOT: $ZBASH_RC"
        echo -e "    EXPECTED OUT: $BASH_OUT"
        echo -e "    ACTUAL OUT:   $ZBASH_OUT"
    fi
}
```

### ทำไมระบบนี้จึงทรงพลังอย่างยิ่งยวด?
1. **ตรวจจับ Edge Cases อัตโนมัติ:** เราไม่ต้องมานั่งคำนวณว่านิพจน์ `${foo:-${bar:=baz}}` ควรได้ค่าอะไร เพราะ Bash ได้คำนวณไว้ให้แล้ว เราเพียงแค่ทำให้ `zbash` ได้ผลลัพธ์ตรงกัน 100%
2. **ป้องกันการถดถอย (No Regressions):** เมื่อมีการปรับปรุงประสิทธิภาพใน C หรือเพิ่มฟังก์ชันใน ARM64 Assembly เราสามารถสั่งรันชุดทดสอบทั้งหมดได้ภายในไม่กี่วินาที หากมีโค้ดส่วนใดกระทบต่อพฤติกรรมเดิม ระบบจะชี้เป้าบรรทัดที่มีปัญหาให้ทันที

## 🧪 5. จาก 100 สู่ 1,000: การยกระดับมาตรฐานคุณภาพ

ในตอนแรกเริ่มโครงการ เราทดสอบเพียง 100 ข้อ แต่สำหรับระบบปฏิบัติการและเชลล์ 100 ข้อยังห่างไกลจากความสมบูรณ์แบบ  
เราจึงตัดสินใจครั้งใหญ่: **ขยายชุดทดสอบเป็น 10 โมดูลอิสระ รวมทั้งสิ้น 1,000 กรณีทดสอบ!**

ครอบคลุมทุกแง่มุมตั้งแต่:
* ตัวแปรและสภาพแวดล้อม
* นิพจน์คณิตศาสตร์แบบซ้อน
* ลูปและเงื่อนไขลึก 4 ชั้น
* ท่อไปป์และทิศทางไฟล์ที่ซับซ้อน
* Subshells และ Grouping
* Indexed Arrays
* อักขระ Unicode ภาษาไทย และ Stress Cases

## 🎯 6. สรุปบทเรียนสำหรับนักพัฒนา

1. **อย่าตั้งโจทย์ความถูกต้องด้วยตัวเอง:** หากคุณกำลังสร้างระบบเพื่อทดแทนมาตรฐานเดิม จงใช้มาตรฐานเดิมนั้นเป็นเครื่องมือตรวจสอบ
2. **Differential Testing คือเกราะคุ้มกันที่ดีที่สุด:** มันช่วยประหยัดเวลาการเขียน Test Case ลงได้มหาศาล และให้ความครอบคลุม (Coverage) ที่ลึกซึ้งกว่า Unit Test ทั่วไปหลายเท่า
3. **ความถูกต้องคือข้อตกลงที่ต่อรองไม่ได้:** การยอมรับความผิดพลาดแม้เพียง 0.1% ในวันนี้ คือจุดเริ่มต้นของการพังทลายของระบบในวันข้างหน้า

ในบทที่ 16 เราจะมา **ผ่าโครงสร้างชุดทดสอบ 10 โมดูล 1,000 ข้อ vs macOS Bash** เพื่อดูว่าในแต่ละหมวดมีกรณีทดสอบอะไรบ้าง และเราผ่านมันมาได้อย่างไร!
