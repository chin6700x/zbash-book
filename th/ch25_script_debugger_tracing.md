## 🧭 1. เมื่อสคริปต์ 1,000 บรรทัดทำงานผิดพลาด

ลองจินตนาการถึงสถานการณ์จริงของวิศวกรระบบและ DevOps:  
คุณมีไฟล์เชลล์สคริปต์ขนาด 1,000 บรรทัดที่ใช้บิลด์ซอฟต์แวร์หรือเดปลอยระบบคลาวด์  
เมื่อสั่งรัน สคริปต์กลับล้มเหลวกลางคันโดยพิมพ์เพียงข้อความสั้นๆ:
```
error: missing file
```
คำถามคือ: **คำสั่งไหนใน 1,000 บรรทัดที่เป็นตัวการ? ตัวแปรตัวไหนมีค่าว่าง? และลูปตัวไหนที่ส่งพารามิเตอร์ผิดพลาด?**

ในโลกของ Bash เครื่องมือที่วิศวกรทั่วโลกใช้กู้วิกฤตนี้เสมอมาคือ **การดีบั๊กผ่าน Execution Tracing**:
```bash
$ zbash -x deploy.sh
```
หรือการแทรกคำสั่ง `set -x` และ `set +x` เฉพาะจุด เพื่อดูคำสั่งที่ถูกแทนที่ค่าตัวแปรแล้วทีละบรรทัดก่อนรันจริง!

คำถามเชิงสถาปัตยกรรมคือ:  
> *"เบื้องหลังตัวเลือก `-x` (xtrace), `-v` (verbose), `-n` (noexec), และ `-e` (errexit) เชลล์ต้องจัดลำดับขั้นตอนการทำงานในระดับภาษา C อย่างไร เพื่อให้การ Tracing มีความแม่นยำและไม่รบกวนผลลัพธ์ของโปรแกรม?"*

ในบทนี้ เราจะมาแกะรอยการสร้าง **ระบบดีบั๊กและตรวจสอบสคริปต์ในตัว (In-Process Debugger Engine)** ของ `zbash` กัน!

## 🏗️ 2. สารบบ 4 เสาหลักของการดีบั๊กใน Shell

ในมาตรฐาน POSIX เชลล์มีแฟล็กสำหรับควบคุมการตรวจสอบและดีบั๊ก 4 ตัวหลัก:

| ตัวเลือก (Flags) | ชื่อโหมด (Mode Name) | สาระสำคัญและพฤติกรรมทางวิศวกรรม |
| :---: | :--- | :--- |
| **`-x`** | **`xtrace` (Execution Trace)** | ขยายตัวแปรและ Wildcards ให้เรียบร้อย แล้วพิมพ์คำสั่งพร้อมเครื่องหมาย `+ ` ออกทาง STDERR ก่อนเริ่มรันจริง |
| **`-v`** | **`verbose` (Verbose Input)** | พิมพ์ข้อความคำสั่งดิบ (Raw Input) ทันทีที่อ่านบรรทัดนั้นเข้ามา ก่อนการขยายตัวแปรใดๆ |
| **`-n`** | **`noexec` (Syntax Dry-Run)** | อ่านและแจงส่วน (Parse) ไวยากรณ์ทั้งหมดเพื่อตรวจหา Syntax Errors แต่ **ไม่สั่งรันคำสั่งจริง** แม้แต่ตัวเดียว |
| **`-e`** | **`errexit` (Exit on Error)** | ยุติการทำงานของสคริปต์ทันทีที่คำสั่งใดคำสั่งหนึ่งคืนค่า Exit Code ไม่เท่ากับศูนย์ ($? \neq 0$) |

## 🔍 3. เจาะลึกโค้ด `xtrace` และ `noexec` ใน `engine.c`

ดูโค้ดจริงใน [`src/core/engine.c`](src/core/engine.c) บรรทัดที่ 2282 ถึง 2310:

```c
/* ไฟล์: src/core/engine.c (บรรทัดที่ 2282 - 2310) */
    /* 1. โหมด xtrace (-x): พิมพ์คำสั่งที่ผ่านการขยายตัวแปรแล้วออกทาง STDERR */
    if (state->xtrace) {
        for (int k = 0; k < pipelines[i].cmd_count; k++) {
            fprintf(stderr, "+ ");
            for (int a = 0; a < pipelines[i].cmds[k].argc; a++) {
                fprintf(stderr, "%s ", pipelines[i].cmds[k].argv[a]);
            }
            fprintf(stderr, "\n");
        }
    }

    /* 2. โหมด noexec (-n): หากเปิดอยู่ จะข้ามการรันคำสั่งจริงทั้งหมด! */
    if (!state->noexec) {
        state->last_status = execute_pipeline(state, &pipelines[i]);
        if (invert) {
            state->last_status = (state->last_status == 0) ? 1 : 0;
        }
    }

    /* 3. ล้างหน่วยความจำคำสั่ง */
    prev_conn = pipelines[i].next_conn;
    for (int k = 0; k < pipelines[i].cmd_count; k++) {
        free_cmd_strings(&pipelines[i].cmds[k]);
    }

    /* 4. โหมด errexit (-e): หยุดสคริปต์ทันทีหากเกิดข้อผิดพลาด */
    if (state->errexit && state->last_status != 0) {
        state->should_exit = true;
        state->exit_code = state->last_status;
        break;
    }
```

### ทำไมการจัดวางลำดับโค้ดตรงนี้จึงสมบูรณ์แบบ?
1. **พิมพ์หลังการขยายตัวแปร (Post-Expansion):** สังเกตว่า `xtrace` ทำงานกับ `pipelines[i].cmds[k].argv` ซึ่งเป็นข้อมูลที่ผ่านการขยายตัวแปรและแทนที่คำสั่ง (`$VAR` และ `$(cmd)`) เรียบร้อยแล้ว ทำให้ผู้ใช้มองเห็นค่าจริงที่โปรแกรมภายนอกได้รับอย่างชัดเจน
2. **พิมพ์ออกทาง `STDERR`:** การส่งข้อความ Tracing ออกช่องทางหมายเลข 2 ทำให้ผลลัพธ์ของโปรแกรมใน `STDOUT (1)` ไม่ถูกปนเปื้อน แม้สคริปต์จะมีการต่อท่อไปป์ `cmd1 | cmd2` ก็ตาม
3. **`noexec` ข้ามการ Execute ได้อย่างปลอดภัย:** ช่วยให้นักพัฒนาสามารถตรวจเช็กความถูกต้องของไวยากรณ์ (Syntax Validation) ของสคริปต์ระบบก่อนส่งขึ้นเซิร์ฟเวอร์จริง โดยไม่ต้องกลัวว่าคำสั่งอันตราย (เช่น `rm -rf /tmp/data`) จะถูกทำงานจริง!

## ⚡ 4. การเปิด/ปิดโหมดขณะทำงานด้วย Builtin `set`

ผู้ใช้ไม่เพียงแต่ส่งแฟล็กผ่านคอมมานด์ไลน์ เช่น `zbash -x script.sh` ได้เท่านั้น แต่ยังสามารถเปิด/ปิดเฉพาะจุดที่ต้องการตรวจสอบได้ผ่านคำสั่งในตัว `set`:

```c
/* โค้ดใน src/builtins/builtins.c บรรทัดที่ 470 - 490 */
    /* set -x เปิดการ Trace / set +x ปิดการ Trace */
    if (strcmp(argv[i], "-x") == 0) state->xtrace = true;
    else if (strcmp(argv[i], "+x") == 0) state->xtrace = false;

    /* set -e เปิดการตัดจบเมื่อ Error / set +e ปิดการตัดจบ */
    else if (strcmp(argv[i], "-e") == 0) state->errexit = true;
    else if (strcmp(argv[i], "+e") == 0) state->errexit = false;
```

สิ่งนี้เปิดโอกาสให้นักพัฒนาเขียนสคริปต์ดีบั๊กเฉพาะท่อนที่มีปัญหา:
```bash
echo "Normal execution..."
set -x  # เริ่มดูการทำงานอย่างละเอียด
temp_var=$(( a * b + 10 ))
process_data "$temp_var"
set +x  # ปิดการ Trace เพื่อให้หน้าจอไม่รก
echo "Done!"
```

## 🧭 5. การติดตามตำแหน่งบรรทัด ($LINENO และ BASH_SOURCE Stack)

เมื่อสคริปต์มีความซับซ้อนและมีการเรียกใช้ `source helper.sh` หรือ `. config.sh` ซ้อนกันหลายไฟล์ เชลล์ต้องรู้เสมอว่าคำสั่งปัจจุบันมาจากไฟล์ไหนและบรรทัดที่เท่าไหร่  
ใน [`include/zbash.h`](include/zbash.h) บรรทัดที่ 51 ถึง 54 เราเก็บสแตกของแหล่งที่มาไว้ในโครงสร้างหลัก:

```c
/* ไฟล์: include/zbash.h (บรรทัดที่ 51 - 54) */
    /* Sourcing & BASH_SOURCE tracking */
    char *source_stack[ZBASH_MAX_SOURCE_DEPTH];
    int source_depth;
```

เมื่อมีการเรียก `source file.sh`:
1. เชลล์จะผลักชื่อไฟล์ใหม่ลงบน `source_stack[source_depth++]`
2. ทุกครั้งที่อ่านแต่ละบรรทัด ตัวนับบรรทัดของไฟล์นั้นจะเพิ่มขึ้น ทำให้ตัวแปร `$LINENO` คืนค่าหมายเลขบรรทัดจริงของไฟล์นั้นได้อย่างแม่นยำ
3. เมื่ออ่านไฟล์เสร็จสิ้น เชลล์จะทำลายและดึงชื่อไฟล์ออกจากสแตก เพื่อคืนบริบทกลับสู่ไฟล์แม่ดั้งเดิมอย่างไร้รอยต่อ

## 🎯 6. สรุปบทเรียนสำหรับนักพัฒนา

1. **เครื่องมือที่ดีต้องโปร่งใสและตรวจสอบได้:** การมีระบบ Debugger และ Tracing ในตัว ทำให้เชลล์ไม่ได้เป็นเพียงแค่เครื่องมือทำงาน แต่เป็นสภาพแวดล้อมการเรียนรู้ที่ช่วยให้นักพัฒนาเข้าใจการทำงานของระบบได้อย่างลึกซึ้ง
2. **STDERR คือช่องทางสื่อสารของระบบ:** การส่งข้อมูล Tracing ออกทาง STDERR คือมาตรฐานที่ช่วยแยกข้อมูลของระบบออกจากข้อมูลของแอปพลิเคชันอย่างเด็ดขาด
3. **การออกแบบ State Machine ที่รัดกุม:** การจัดวางแฟล็ก `xtrace`, `noexec`, และ `errexit` ในจุดศูนย์กลางของ Execution Loop ช่วยให้เราเพิ่มความสามารถในการตรวจสอบระดับมืออาชีพได้ด้วยโค้ดเพียงไม่กี่สิบบรรทัด
