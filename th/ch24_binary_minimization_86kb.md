## 🧭 1. มนต์ดำแห่งความกะทัดรัด: 86 KB vs 1.9 MB

เมื่อคุณสั่งตรวจสอบขนาดของไบนารีสองตัวบนเครื่อง Mac:
```bash
$ ls -lh /bin/bash bin/zbash
-rwxr-xr-x  1 root  wheel  1.9M  /bin/bash
-rwxr-xr-x  1 dev   staff   86K  bin/zbash
```
ตัวเลขนี้มักทำให้วิศวกรทุกคนต้องตกตะลึง:
* GNU Bash ดั้งเดิมมีขนาด **1,900 KB (1.9 MB)**
* ในขณะที่ `zbash` มีขนาดเพียง **86 KB** เท่านั้น!

ขนาดที่เล็กลงกว่า **22 เท่า** นี้ ไม่ได้แลกมาด้วยการตัดทอนความสามารถ เพราะ `zbash` ผ่านชุดทดสอบ Parity 1,000 จาก 1,000 ข้อ (100.0%) และรองรับทั้ง Loops, Pipes, Arrays, Arithmetic, Subshells, และ SIMD Lexer ครบถ้วน

คำถามทางวิศวกรรมคือ:  
> *"เราทำได้อย่างไร? ในยุคที่ซอฟต์แวร์ทั่วไปมักมีขนาดหลายสิบถึงหลายร้อยเมกะไบต์ อะไรคือความลับในการรีดไบนารีภาษา C ให้เหลือเพียง 86 KB?"*

ในบทนี้ เราจะมาผ่าโครงสร้าง Mach-O Binary, แกะรอย Linker Flags ใน `Makefile`, และเปิดเผยศิลปะการตัดโค้ดส่วนที่ไม่ได้ถูกเรียกใช้งาน (Dead Code Elimination) ในระดับไบต์!

## 🏗️ 2. ผ่ากายวิภาคของ Mach-O และ ELF Binary

เมื่อคอมไพเลอร์ (Clang หรือ GCC) แปลงโค้ดภาษา C ออกมาเป็นไฟล์ที่รันได้ ไบนารีจะถูกแบ่งออกเป็น 3 เซกเมนต์หลัก:

```
                            [ Mach-O Binary Anatomy ]
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
 [ __TEXT Segment ]              [ __DATA Segment ]            [ __LINKEDIT Segment ]
 • __text (Machine Code)         • __data (Global ตัวแปร)      • Symbol Table (ชื่อฟังก์ชัน)
 • __cstring (ข้อความสตริง)      • __bss (ตัวแปรค่าว่าง)        • Dynamic Loader Info (dyld)
 • Read-only (ห้ามแก้ไข)         • Read-Write (แก้ไขได้)        • Export / Import Tables
```

### สาเหตุที่โปรแกรมทั่วไปมีขนาดใหญ่ (Binary Bloat):
1. **การดึงสัญลักษณ์ที่ไม่ได้ใช้เข้ามา (Unused Symbols):** หากเราเขียน `printf()` เพียงครั้งเดียว ลิงก์เกอร์แบบดั้งเดิมอาจดึงโค้ดฟอร์แมตตัวเลข Floating-point ทั้งระบบเข้ามาด้วย
2. **ตารางสัญลักษณ์และสตริงดีบั๊กที่ค้างอยู่ (Debug Overhead):** ชื่อฟังก์ชัน, ชื่อตัวแปร, และ Line Numbers ที่ใส่ไว้สำหรับ Debugger อาจกินพื้นที่มากกว่า 60% ของขนาดไฟล์ทั้งหมด!
3. **การขาดการเชื่อมโยงข้ามไฟล์ (No Cross-Module Optimization):** คอมไพเลอร์มองเห็นโค้ดทีละไฟล์ ทำให้ไม่สามารถตัดฟังก์ชันที่ไม่เคยถูกเรียกในไฟล์อื่นทิ้งได้

## 🔍 3. เจาะลึก Compiler Flags ใน `Makefile`

ดูโค้ดจริงใน [`Makefile`](Makefile) บรรทัดที่ 11 ถึง 20:

```makefile
# ไฟล์: Makefile (บรรทัดที่ 11 - 20)
CC ?= clang
CFLAGS = -O3 -Wall -Wextra -pthread -fomit-frame-pointer -flto -Iinclude
ASFLAGS = -O3 -Wall

ifeq ($(UNAME_S),Darwin)
    LDFLAGS = -Wl,-dead_strip -Wl,-fixup_chains
else
    CFLAGS += -D_GNU_SOURCE
    LDFLAGS = -Wl,--gc-sections
endif
```

ทุกตัวเลือก (Flags) ในบรรทัดเหล่านี้ ถูกคำนวณมาอย่างประณีตทางวิศวกรรม:

### 1. `-flto` (Link-Time Optimization)
ตามปกติ คอมไพเลอร์จะคอมไพล์ `engine.c`, `lexer.c`, `builtins.c` แยกกันเป็น `.o` โดยไม่รู้ว่าไฟล์อื่นทำอะไร  
แต่ด้วย `-flto`:
* คอมไพเลอร์จะส่งต่อโค้ดระดับ Intermediate Representation (LLVM Bitcode) ไปให้ Linker
* ทำให้ Linker สามารถมองเห็นโค้ดทั้งระบบพร้อมกัน ทำการ **Inline ข้ามไฟล์** และยุบโค้ดที่ซ้ำซ้อนทิ้งได้อย่างทรงพลัง!

### 2. `-fomit-frame-pointer`
สั่งให้คอมไพเลอร์ไม่ต้องสร้าง Frame Pointer (`push rbp` หรือ `stp x29, x30, [sp]`) ในฟังก์ชันที่ไม่จำเป็น:
* **ประหยัดคำสั่ง:** ลดคำสั่ง Prologue/Epilogue ไปฟังก์ชันละ 2-4 คำสั่ง
* **เพิ่มรีจิสเตอร์:** ปลดปล่อยรีจิสเตอร์ `x29` บน ARM64 ให้กลายเป็น General Purpose Register เพิ่มขึ้นอีก 1 ตัว ทำให้ซีพียูไม่ต้องสลับตัวแปรลงหน่วยความจำ!

## ⚡ 4. ศาสตร์แห่ง Linker Dead Code Stripping

นี่คือหมัดเด็ดที่สุดที่ตัดลดขนาดไฟล์ลงได้ถึง 40%!

### บน macOS Darwin: `-Wl,-dead_strip`
คำสั่งนี้บอก Linker ของ Apple ว่า:  
> *"จงเริ่มต้นจากฟังก์ชัน `_main` แล้วลากเส้นกราฟการเรียกใช้งาน (Call Graph) ไปยังทุกฟังก์ชัน หากมีฟังก์ชันใดหรือข้อมูลก้อนใดในไฟล์ `.o` ที่ไม่มีเส้นทางเดินไปถึง **จงทำลายและตัดทิ้งออกจากไบนารีทันที!**"*

### บน Linux: `-Wl,--gc-sections`
ทำงานในลักษณะเดียวกัน โดยทำการ Garbage Collection ให้กับ Section ของโค้ดที่ไม่ถูกเรียกใช้งาน

### การล้างตารางสัญลักษณ์ด้วย `strip`
หลังจากได้ไฟล์ไบนารีมา เราสามารถสั่ง:
```bash
strip -x bin/zbash
```
เพื่อลบ Local Symbols และ Debug Info ที่ไม่จำเป็นสำหรับการรันจริงทิ้ง ทำให้พื้นที่ในเซกเมนต์ `__LINKEDIT` หดเล็กลงเหลือเพียงไม่กี่กิโลไบต์!

## 🛡️ 5. ศิลปะการเขียน C เพื่อหลีกเลี่ยง Libc Bloat

นอกจาก Flags ของคอมไพเลอร์แล้ว **วิธีการเขียนโค้ดภาษา C ของตัวโปรแกรมเมอร์เอง** คือปัจจัยที่สำคัญที่สุด:

| สิ่งที่ควรหลีกเลี่ยง (Bloat Patterns) | ทางเลือกใน `zbash` (Bare-Metal Patterns) | ผลลัพธ์ทางวิศวกรรม |
| :--- | :--- | :--- |
| **`printf("%f", val)`** | ใช้การแปลงจำนวนเต็ม `snprintf` หรือ Integer Math | ตัด Math Floating-point Library ทิ้งทั้งระบบ |
| **ไลบรารี Regex ภายนอก (`pcre`)** | เขียน State Machine สแกนเนอร์ใน Pure C เอง | ประหยัดพื้นที่ไบนารีไปกว่า 500 KB |
| **GNU Readline / Ncurses** | ควบคุม Terminal Raw Mode ด้วย VT100 เอง (บทที่ 20) | ประหยัดพื้นที่ไบนารีไปกว่า 800 KB |
| **ตัวสร้าง Grammar (`yacc` / `bison`)** | เขียน Recursive Descent Parser ด้วยมือ | ไร้ตาราง Lookahead หนักๆ โค้ดเหลือขนาดจิ๋ว |

## 🎯 7. สรุปบทเรียนสำหรับนักพัฒนา

1. **ขนาดของไบนารีสะท้อนถึงความสะอาดของสถาปัตยกรรม:** โปรแกรมขนาด 86 KB ที่ทำงานได้เทียบเท่าโปรแกรม 1.9 MB คือเครื่องพิสูจน์ว่า เราไม่มีโค้ดส่วนเกินที่ไม่ได้ใช้งานแฝงอยู่เลย
2. **ควบคุม Build Pipeline ให้ถึงระดับ Linker:** การเข้าใจว่า `-flto` และ `-dead_strip` ทำงานอย่างไร ช่วยให้คุณเค้นประสิทธิภาพจากคอมไพเลอร์ได้สูงสุด
3. **พึ่งพาเฉพาะมาตรฐานพื้นฐาน:** การเขียน C ที่พึ่งพาเพียงระบบปฏิบัติการ ทำให้โปรแกรมมีขนาดเล็ก พกพาสะดวก และมีความเสถียรระดับหินผา
