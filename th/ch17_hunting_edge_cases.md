## 🧭 1. เรื่องเล่าจากสนามรบจริง (Battlefield Chronicles)

ไม่มีทางที่ระบบซอฟต์แวร์ระดับระบบปฏิบัติการจะถูกเขียนขึ้นมาได้อย่างไร้ที่ติในคราวเดียว  
ความสมบูรณ์แบบ 1,000 จาก 1,000 การทดสอบของ `zbash` ไม่ได้เกิดขึ้นเพราะโชคช่วย แต่เกิดขึ้นจากการล่าบั๊กอย่างไม่ลดละตลอดหลายสัปดาห์

ในการสร้าง Shell มีบั๊กหลายประเภทที่ไม่แสดงอาการเมื่อรันคำสั่งเดี่ยวๆ บนหน้าจอ แต่จะปรากฏตัวขึ้นมาทันทีเมื่อเจอกับสคริปต์ที่ซับซ้อน หรือรันต่อเนื่องเป็นหมื่นรอบในระบบจริง  
ในบทนี้ เราจะมาเปิดบันทึกภาคสนาม **"5 บั๊กสุดแสบ"** ที่เราค้นพบระหว่างการทดสอบ Parity และวิธีที่เรากำราบพวกมันด้วยภาษา C แบบเด็ดขาด!

## 🪲 บั๊กที่ 1: ท่อไปป์ค้างนิรันดร์ (The Forgotten Pipe Hang)

### 📌 อาการของบั๊ก:
เมื่อเรารันสคริปต์ที่มี Pipeline ซ้อนกัน เช่น:
```bash
cat data.csv | grep "active" | wc -l
```
โปรแกรมกลับค้างสนิท (Hang) นิ่งอยู่อย่างนั้น ไม่ยอมคืนพรอมต์กลับมา และ CPU ทำงานเป็น 0%

### 🔍 การสืบสวนหาสาเหตุ:
เมื่อใช้เครื่องมืออย่าง `lsof` ตรวจสอบ File Descriptors ของโปรเซส เราพบว่าโปรเซส `wc -l` ยังไม่ยอมจบการทำงาน เพราะมันยังรอรับข้อมูลจาก STDIN  
คำถามคือ: `grep` ก็ทำงานจบและปิดตัวไปแล้ว ทำไม `wc` ถึงไม่ได้รับสัญญาณ **End-of-File (EOF)**?

**ความจริงที่ค้นพบ:**  
ในฟังก์ชันสร้างท่อไปป์ ตัว Parent Process (ตัว `zbash` เอง) ได้เรียก `pipe()` เพื่อสร้างท่อ แต่ **ลืมสั่ง `close()` ปลายท่อเขียน (`pipe_fds[1]`) ในตัวมันเอง!**  
เคอร์เนลจึงมองว่า *"ยังมีโปรแกรมตัวหนึ่ง (คือตัวเชลล์แม่) ที่ยังถือท่อเขียนนี้อยู่ ดังนั้นท่อยังไม่ปิดอย่างสมบูรณ์"* ตัวรับอย่าง `wc` จึงต้องรอคอยข้อมูลต่อไปชั่วนิรันดร์!

### 🛠️ วิธีแก้ในโค้ด:
ดูโค้ดแก้ไขใน [`src/core/engine.c`](src/core/engine.c) บรรทัดที่ 1076 ถึง 1079:
```c
/* ไฟล์: src/core/engine.c */
    /* กฎเหล็ก: ทันทีที่ Fork ลูกครบทุกตัว Parent ต้องปิดปลายท่อทั้งหมดทันที! */
    for (int j = 0; j < n - 1; j++) {
        close(pipe_fds[j][0]);
        close(pipe_fds[j][1]);
    }
```
ทันทีที่เพิ่มลูปปิดท่อใน Parent สัญญาณ EOF ก็ไหลเข้าสู่ปลายทางอย่างถูกต้อง และคำสั่ง Pipeline ทั้งหมดกลับมาทำงานรวดเร็วในพริบตา!

## 🪲 บั๊กที่ 2: สิ้นเสียงจากคีย์บอร์ดหลังลูป (`done < file`)

### 📌 อาการของบั๊ก:
ในชุดทดสอบข้อที่ #77 (`test_07_pipelines_redirections.sh`):
```bash
while read line; do
    echo "Item: $line"
done < file.txt

read user_input # บรรทัดนี้ไม่รอรับค่าจากผู้ใช้ แต่ข้ามไปทันที!
```

### 🔍 การสืบสวนหาสาเหตุ:
เมื่อลูป `while` มีการเปลี่ยนทิศทางไฟล์ด้วย `< file.txt` ตัว Engine ได้ทำการเรียก `dup2(fd, STDIN_FILENO)` เพื่อเปลี่ยนช่องทางรับข้อมูลของตัวลูป  
แต่เพราะตัวลูปทำงานในกระบวนการหลัก การเปลี่ยน `STDIN_FILENO` จึงส่งผลให้ตัวอธิบายไฟล์ของคีย์บอร์ดถูกทำลายไปตลอดกาล! เมื่อไฟล์อ่านหมด เชลล์จึงติดอยู่ในสถานะ EOF

### 🛠️ วิธีแก้ในโค้ด:
ดูโค้ดแก้ไขใน [`src/core/engine.c`](src/core/engine.c) บรรทัดที่ 1456 ถึง 1510:
```c
    /* จำท่อเดิมไว้ก่อนเข้าลูป */
    saved_in = dup(STDIN_FILENO);
    apply_redirections(&redir_cmd);

    /* รันลูปจนจบ... */

    /* กู้คืนท่อเดิมกลับมายัง Terminal */
    dup2(saved_in, STDIN_FILENO);
    close(saved_in);
```
การจำและกู้คืนช่องทาง I/O แก้ปัญหานี้ได้อย่างสมบูรณ์แบบ 100%

## 🪲 บั๊กที่ 3: ตัวแปร Local ทะลุข้ามมิติใน Recursive Function

### 📌 อาการของบั๊ก:
เมื่อมีฟังก์ชันเรียกตัวเองซ้ำๆ (Recursion) เช่น การคำนวณแฟกทอเรียล:
```bash
factorial() {
    local n=$1
    if [ "$n" -le 1 ]; then
        echo 1
        return
    fi
    local prev=$(factorial $(( n - 1 )))
    echo $(( n * prev ))
}
```
ผลลัพธ์ที่ได้กลับผิดเพี้ยนไปหมด เพราะค่าของ `n` ในชั้นนอกถูกค่าของ `n` ในชั้นในเขียนทับ!

### 🔍 การสืบสวนหาสาเหตุ:
ในตอนแรกเราเก็บตัวแปร `local` ผ่าน `setenv()` ธรรมดา โดยไม่มีการจำค่าเดิมของชั้นก่อนหน้า เมื่อฟังก์ชันชั้นในสั่ง `local n=1` มันจึงไปทับค่า `n=5` ของชั้นนอกอย่างถาวร

### 🛠️ วิธีแก้ในโค้ด:
เราสร้าง **Call Scope Stack** ใน [`include/zbash.h`](include/zbash.h) บรรทัดที่ 65 ถึง 70:
```c
    struct {
        char *name;
        char *old_val;
        bool was_set;
    } local_vars[512];
    int local_var_count;
```
ทุกครั้งที่มีการประกาศ `local` เราจะบันทึกค่าเดิมไว้บนสแตก และเมื่อออกจากฟังก์ชัน เราจะแกะสแตกถอยหลัง (Unwind) เพื่อกู้คืนค่าเดิมกลับมาเสมอ ทำให้การคำนวณแบบ Recursion ทำงานได้อย่างถูกต้องไร้ที่ติ!

## 🪲 บั๊กที่ 4: ขยะ Inode ล้นดิสก์จาก Here-Strings (`<<<`)

### 📌 อาการของบั๊ก:
ในการรัน Stress Test หมื่นรอบ เครื่องเกิดอาการแจ้งเตือนว่าดิสก์เต็ม ทั้งๆ ที่พื้นที่ว่าง (GB) ยังเหลือมหาศาล!

### 🔍 การสืบสวนหาสาเหตุ:
เมื่อตรวจด้วยคำสั่ง `df -i` พบว่า **Inodes ของระบบไฟล์เต็ม 100%!**  
สาเหตุเกิดจากคำสั่ง Here-String (`cmd <<< "text"`) มีการสร้างไฟล์ชั่วคราวใน `/tmp/zbash_hs_XXXXXX` เพื่อส่งให้โปรแกรมอ่าน แต่หลังจากคำสั่งทำงานจบ โค้ดไม่ได้สั่งลบไฟล์นั้นทิ้ง!

### 🛠️ วิธีแก้ในโค้ด:
ดูโค้ดแก้ไขใน [`src/core/engine.c`](src/core/engine.c) บรรทัดที่ 768 ถึง 771:
```c
    if (cmd->in_file) {
        if (strncmp(cmd->in_file, "/tmp/zbash_hs_", 14) == 0) {
            unlink(cmd->in_file); /* สั่งทำลาย Inode ทิ้งทันที! */
        }
        free(cmd->in_file);
    }
```
ไฟล์ชั่วคราวถูกล้างทิ้งทันทีในหน่วยมิลลิวินาที ป้องกันขยะ Inode ค้างในระบบอย่างถาวร

## 🪲 บั๊กที่ 5: การหารด้วยศูนย์พังทั้งจักรวาล (SIGFPE Crash)

### 📌 อาการของบั๊ก:
เมื่อผู้ใช้เขียนสูตรคณิตศาสตร์ผิดพลาด เช่น:
```bash
echo $(( 10 / 0 ))
```
แทนที่เชลล์จะแจ้งเตือนข้อผิดพลาดแล้วทำงานต่อ เชลล์กลับเกิดอาการ **Crash กะทันหัน** ด้วยสัญญาณ `Floating point exception: 8 (SIGFPE)`

### 🔍 การสืบสวนหาสาเหตุ:
ในสถาปัตยกรรม CPU ส่วนใหญ่ (รวมถึง ARM64 และ x86) การนำจำนวนเต็มมาหารด้วยศูนย์ หรือทำ Modulo ด้วยศูนย์ ในระดับภาษา C (`a / b`) จะทำให้ฮาร์ดแวร์ส่งสัญญาณ Interrupt สั่งประหารโปรเซสทันที!

### 🛠️ วิธีแก้ในโค้ด:
ดูโค้ดป้องกันใน [`src/core/engine.c`](src/core/engine.c) บรรทัดที่ 326 ถึง 335:
```c
    if (op == '/' || op == '%') {
        if (b == 0) {
            fprintf(stderr, "zbash: division by 0\n");
            state->last_status = 1;
            return 0; /* ดักจับในซอฟต์แวร์ก่อนถึงระดับฮาร์ดแวร์! */
        }
        val = (op == '/') ? (val / b) : (val % b);
    }
```
การดักตรวจสอบก่อนส่งให้ CPU ทำงาน ทำให้ `zbash` ปลอดภัยจากการแครช คืนค่า Exit Code 1 และพิมพ์ข้อความเตือนเหมือน GNU Bash ทุกประการ
